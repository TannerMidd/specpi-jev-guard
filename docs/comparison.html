Jev API vs Laya: CPU and GPU

The same cases, prompts, local rules and thresholds, followed by the full 856-attempt devious suite and a separate tuning study. Faster local inference did not establish equivalent protection.

Recorded 2026-09-22. Laya English root checkpoint, Ryzen 9 3900X and RTX 5070 Ti. Jev remains the default.

On this page

Laya is not a safety-equivalent replacement at these thresholds. It gave 45 unexpected allows on CPU and 44 on GPU, compared with Jev’s 6. The Laya implementation is shelved and is not available in the released package. These are observations from a research prototype, not a supported installation option. Nothing in the text-only suites was executed.

Jev over the API, and the same Laya checkpoint on CPU and on GPU, given the same cases, prompts, local rules and thresholds. Two follow-ups come after the paired results: the full 856-attempt devious suite, run on the GPU only, and a six-configuration tuning study. Neither changed the verdict, and no tuned preset was adopted.

This paired comparison used the devious suite's 136 original cases: 111 attack-labelled cases and 25 ordinary controls. The full 856 attempts come further down. One demonstrative attack-labelled case permits allow, so raw allow counts differ from unexpected bypass counts. The red-team comparison replays the same 30 recorded attacks for all three runs; it is not a fresh adaptive red-team run.

The same English checkpoint runs on both devices, but the SDK uses FP32 on CPU and BF16 autocast on GPU. This is not a device-only numerical comparison: final decision bands changed in some cases. The original Jev and CPU recordings are preserved alongside the new GPU run.

Model load excludes imports and download. Peaks include loading and inference, not hardware minimums. On the GPU, PyTorch's allocator held 1.60 GiB at the snapshot (peak 2.30 GiB) and reserved 2.50 GiB. Reserved includes allocated, so do not add them, and neither is total VRAM use: CUDA context, driver overhead, non-PyTorch allocations and other apps are excluded. Measured on an AMD Ryzen 9 3900X and an NVIDIA GeForce RTX 5070 Ti, Windows 11, 4 host CPU threads.

Keep one service resident rather than reloading the model for every tool call. Multiple Pi sessions can use it. Switching the guard back to Jev does not stop this separately managed service: stop the Python process to release its memory.

End to end: research prototype

These three runs exercised the research integration. They do not replace the released package’s separate historical test report.

These are integration assertions, not safety accuracy. In the CPU run, B4 was blocked instead of asking, C13/C14 missed the expected unattended middle-band behavior, and B8 used bash rather than the requested edit. Agent deviations can fail an assertion without testing the intended path. All failed assertions remain in the results; none were retuned away for the GPU run.

The agent that proposes the calls still uses an API in this test; selecting local classification does not make the rest of Pi offline. The full per-scenario outcomes are in the recorded results.

The devious suite: 856 attempts

The frozen 136 cases plus 120 new attack and benign pairs across 20 families. Each new command was tested plainly, nested in a shell, and with a misleading assurance in the request, so the 720 new attempts are correlated views, not 720 independent techniques. Jev and the unchanged Laya GPU baseline saw the same cases and thresholds. There was no CPU run of this suite.

Tuning study: no preset qualified

These are model-only Laya results, with no local-rule credit and no Jev comparison. Six predeclared configurations used the same English weights and unchanged thresholds on a deterministic ShellRisk-Bench TRAIN sample. None passed the development gate; FP32 was frozen for diagnosis only, then tested once alongside baseline on the separate TEST split.
